# ⌨️ CLI Reference

> `./bin/devbox` is the single entrypoint for both machines — the Linux workstation that runs the container and the
> macOS laptop. It is generated by [bashly](https://bashly.dev) from authored sources in `cli/`; this page is both the
> user reference and the maintainer contract for changing it.

**Related:** [Installation](installation.md) · [Connecting](connecting.md) · [Git Identities](git.md) ·
[Operations](operations.md) · [Development](development.md)

---

## 📍 At a glance

| Audience           | Use this                                                                                           |
| ------------------ | -------------------------------------------------------------------------------------------------- |
| CLI users          | `./bin/devbox` from the repo root, or `devbox` anywhere after [`devbox install`](#-devbox-install) |
| CLI maintainers    | Edit authored sources in `cli/` (see [Maintainer workflow](#-maintainer-workflow))                 |
| Generated artifact | `bin/devbox` is generated, committed build output, not the source of truth                         |
| AI agents          | The `devbox-cli` skill: which side runs what, the guards an agent leaves in place                  |

> [!IMPORTANT]
> Never hand-edit `bin/devbox`. Update the authored bashly sources in `cli/` and regenerate it instead.

### Cheat sheet

```bash
./bin/devbox deploy <workstation> --start   # deploy + start (keeps state; asks before killing SSH sessions)
ssh devbox                           # shell in the container
ssh -A devbox                        # + push, pull, sign as yourself (forwards the 1Password agent)
herdr                                # attach panes; they survive client exit
ssh -N -L 5173:localhost:5173 devbox # reach a dev server
ssh devbox 'cd projects/app && docker compose up -d && devbox-ports'  # project containers on localhost
ssh <workstation> 'cd ~/devbox && ./bin/devbox doctor'
ssh <workstation> 'cd ~/devbox && ./bin/devbox sessions'   # who is connected (a recreate kills them)
./bin/devbox sync omp                # apply the repo's OMP preset to this laptop and the devbox
./bin/devbox sync claude             # merge the repo's Claude Code preset into this laptop's and the devbox's settings
./bin/devbox install                 # devbox on the PATH, with bash completion (deploy does the workstation)
./bin/devbox agent install           # laptop-side: same agent git override as the devbox
./bin/devbox doctor laptop           # laptop-side acceptance test: keys, configs, override, tokens
./bin/devbox sync identities         # push this laptop's identity registry into the devbox
./bin/devbox sync profile            # render your profile.json into the agent context on both machines
```

## 🗂️ Command groups

Every command is side-guarded: **workstation** commands run only on the Linux host that runs the container (not inside
it), **laptop** commands only on macOS, and `install`, `doctor` and `completions` on either. Running a command on the
wrong side exits with a one-line message naming the right one. Log prefixes `[INFO]`, `[OK]`, `[WARN]`, `[ERROR]` are
the same on both.

| Group       | Commands                                                                                                                        | Side guard                                        |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------- |
| Workstation | `env`, `start`, `stop`, `rebuild`, `bootstrap`, `skills`, `shell`, `sessions`, `logs`, `hook`, `update`, `keys`, `docker setup` | Linux host that runs the container, not inside it |
| Laptop      | `deploy`, `sync omp`, `sync claude`, `sync identities`, `sync profile`, `agent install`                                         | macOS only                                        |
| Both        | `install`, `doctor`, `completions`                                                                                              | Either side                                       |

`./bin/devbox --help` lists them, `./bin/devbox <command> --help` shows one command's flags, and `--version`/`-v` prints
the version. `docker`, `sync` and `agent` are only groups: bare, they print their subcommands.

```bash
./bin/devbox --help
./bin/devbox <command> --help
```

## 🧰 Requirements

The laptop needs **bash >= 4.2**: bashly-generated scripts refuse to start on anything older, and macOS's `/bin/bash` is
3.2. `brew install bash` puts a current one where `/usr/bin/env bash` finds it. The workstation's Ubuntu bash is fine.
The scripts that are _not_ generated — `home/.local/libexec/devbox-identities`, the agent launchers and shims — stay
bash 3.2 compatible, since they run under whatever bash the laptop resolves.

## 🖥️ Workstation commands

Run these on the workstation, from the repo (`~/devbox`); from the laptop, prefix them with `ssh <workstation> 'cd
~/devbox && ...'`. Commands that drive the container read `.env` and, if it is missing, fail pointing at `./bin/devbox
env` and `.env.example`.

> [!WARNING]
> `start`, `stop` and `rebuild` count established SSH sessions first: recreating or stopping kills them mid-keystroke
> with no client output, so live sessions get a terminal prompt, or refusal in a script; `--force`/`-f` skips it. A
> `docker compose up` that changes nothing leaves the container running, so a no-op `start` never asks. `update` never
> asks: it only execs into the running container.

| Command                  | What it does                                                                                                                                                         |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `env`                    | Create `.env` from `.env.example` and sync `BIND_ADDR`, `HOST_UID` and `HOST_GID` — see [`devbox env`](#devbox-env)                                                  |
| `start [--force\|-f]`    | Preflight, then build and start the container, recreating it when the repo changed — see [`devbox start`](#devbox-start)                                             |
| `stop [--force\|-f]`     | Stop and remove the container: `docker compose down`. Bind mount and `.env` untouched                                                                                |
| `rebuild [--force\|-f]`  | Rebuild the image from scratch and restart: `docker compose build --no-cache && docker compose up -d`. Use after a `Dockerfile` change                               |
| `bootstrap`              | Re-run the in-container user setup: `docker compose exec` of `container/bootstrap.sh`; idempotent, reprints the checklist                                            |
| `skills`                 | Install the optional agent skills and agent-browser — see [`devbox skills`](#devbox-skills)                                                                          |
| `shell`                  | Open a login shell inside the container: `docker compose exec -it devbox bash -l`. Works even with sshd or Tailscale broken                                          |
| `sessions`               | List the SSH sessions connected to the container: established sshd connections plus the last 10 `Accepted`/`Disconnected` lines, tracing a disconnect after the fact |
| `logs [--follow\|-f]`    | Show the container logs (last 100 lines): `--tail 100` by default; `--follow`/`-f` follows                                                                           |
| `hook [--update\|-u]`    | Restart the moshi-hook daemon in place, without touching SSH sessions — see [`devbox hook`](#devbox-hook)                                                            |
| `update`                 | Upgrade OMP, Claude Code, Codex and moshi-hook inside the running container, then restart the moshi-hook daemon; no rebuild — see [`devbox update`](#devbox-update)  |
| `keys`                   | Print the installed identity public keys and the sshd host-key fingerprint — see [`devbox keys`](#devbox-keys)                                                       |
| `docker setup [--check]` | Provision the rootless project Docker daemon (needs sudo) — see [`devbox docker setup`](#devbox-docker-setup)                                                        |

### `devbox env`

Never clobbers `.env`; sets `BIND_ADDR` from `tailscale ip -4` (left unset, with a warning, when Tailscale has no
address yet), `HOST_UID`/`HOST_GID` from `dev` if present, else invoking user.

### `devbox start`

```
Usage: ./bin/devbox start [--force|-f]
```

Preflight, then `docker compose build` and `docker compose up -d`. The preflight checks:

- `BIND_ADDR` non-empty
- `DEVBOX_DATA_DIR` present, owned `HOST_UID:HOST_GID`, `install -d`'d if absent
- a missing project Docker socket only _warns_, toward `sudo ./bin/devbox docker setup`

Build precedes the session check — a fresh image alone justifies recreating. `start` is how a repo change reaches the
container (a new image or config recreates it); [`update`](#devbox-update) upgrades the agent tools in the running
container instead and never rebuilds or recreates it.

### `devbox skills`

`docker compose exec` of `container/skills.sh`: two global agent skills plus `agent-browser`'s CLI and Chrome build.
Optional, idempotent, kept separate from `bootstrap` — first run downloads ~180 MB. See
[Toolchain](toolchain.md#-agent-skills-and-browser-automation).

### `devbox hook`

Stops and restarts `moshi-hook` via detached `docker compose exec`, prints `moshi-hook status`. Non-destructive: the
daemon is a child of the entrypoint; alternative is recreating the container, killing every SSH session. Needed after
`moshi-hook pair` or a crash. `--update`/`-u` first runs `moshi-hook update` and `moshi-hook install` (every agent whose
config directory exists; it creates none); a failed update aborts before the running daemon is stopped. See
[Toolchain](toolchain.md#-moshi-and-moshi-hook).

### `devbox update`

One command for the four self-updating tools on the bind mount, pane-safe like `hook`: `omp update`, `claude update` and
`codex update` (all through the launchers' `update` passthrough,
[Git Identities](git.md#updates-omp-update-claude-update)), then `moshi-hook update`, `moshi-hook install` (hooks for
every agent it finds, after the agents updated their configs) and the daemon restart. A failed updater is reported and
the others still run; the exit status counts the failures. `moshi-hook install` runs even after a failed
`moshi-hook update`, which only skips the restart, leaving the old daemon serving. Running agent sessions keep their old
binary until restarted.

### `devbox keys`

One row per registry identity: its slug, ssh tag, orgs, and its two public keys (`id_<slug>.pub`, `signing_<slug>.pub`,
or `not set - <field> for [<slug>] in identities.conf` if either is empty), plus the sshd host-key fingerprint. Reads
from the running container when it's up, else straight from `${DEVBOX_DATA_DIR}/.config/devbox/identities.conf`, naming
which source it used. Not a paste target — your laptop's own keys, already on GitHub.

### `devbox docker setup`

```
Usage: sudo ./bin/devbox docker setup [--check]
```

Host-side, one-time provisioning for the project Docker daemon: a second, rootless `dockerd` running as dedicated
unprivileged host user `dev` (uid 1001, group `devbox`) — never the host's root daemon, never nested in the container.
See [Docker](docker.md).

Requires `sudo` (`--check` too: it probes as the daemon's user and reads root-owned units); every step is idempotent, so
re-runs are no-ops once everything is current. `--check` reports what's missing, changes nothing. It needs `.env` to
exist first (`./bin/devbox env`).

> [!WARNING]
> When the `user@1001.service` drop-in changed, or the running manager's environment lacks
> `XDG_CONFIG_HOME=/etc/devbox-docker/config` (it predates the drop-in), `docker setup` restarts `dev`'s user manager —
> and with it the project daemon and every project container. Ubuntu's `user@` stop timeout (5 s) SIGKILLs a container
> slower to stop; one without a restart policy stays down until its `docker compose up -d`. The devbox itself runs on
> the host's root daemon and is untouched.

As root it never follows a path inside the bind mount: the ownership fix-up is a `chown -R` that never follows
symlinks, and everything else there — removing the `docker.service` and wants link
an earlier `systemctl --user enable` left in `~/.config/systemd/user` — runs as `dev`, so a symlink planted from the
devbox can't steer a root `rm`. Every `docker` call it makes as `dev` runs with `DOCKER_CONFIG` outside `/home/dev`, so
`~/.docker/config.json` and `~/.docker/cli-plugins` from the bind mount are never read or executed on the host.

What it provisions:

| Step           | What it does                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Packages       | Installs `uidmap` and `slirp4netns`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| Host user      | Creates `dev:devbox` host user (uid 1001): no password, no sudo, no host login (next row)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| Host sshd      | Checks `sshd -t` first — a config that already fails is reported with sshd's own error — then writes `/etc/ssh/sshd_config.d/devbox-docker.conf` (`DenyUsers dev`), validates again (a failure removes the file and shows sshd's error) and reloads, confirming `sshd -T` denies `dev`. `--check` reports a missing or stale file as one failure and confirms with `sshd -T` only once the file matches. A failing check fails the step, not the run: the remaining steps still go ahead, and setup then exits non-zero with `N step(s) could not be applied`. `dev`'s `~/.ssh` is the bind mount, so a key the container writes there must not open a host login                                                                                                                                                                                                                                                                           |
| Data directory | Moves `DEVBOX_DATA_DIR` to `/home/dev`, chowning it so host and container bind-mount paths match                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| User manager   | Writes `/etc/systemd/system/user@1001.service.d/devbox-docker.conf` pointing dev's `XDG_CONFIG_HOME`/`XDG_DATA_HOME` at root-owned `/etc/devbox-docker` and links the unit there, then reloads systemd — right after the data directory, before anything can start `user@1001`: the firewall unit's `Wants=` pulls it in when the firewall step restarts that unit, and linger starts it. So even a first provisioning's user manager starts on `/etc/devbox-docker`, never on the bind mount. Once the systemd unit below is written, restarts `user@1001.service` when the drop-in changed or the running manager lacks that environment (warning above)                                                                                                                                                                                                                                                                                  |
| Firewall       | Writes `/etc/nftables.d/devbox-docker.nft` and `devbox-docker-firewall.service`, enabling it: keeps published project ports off every interface but loopback and the devbox bridge; keeps the host's own services (its sshd) and the Tailnet overlay (`tailscale0`, Tailscale's address ranges) away from the devbox, its project containers and every process running as dev's uid or one of its subordinate uids (its `/etc/subuid` ranges, read when the ruleset is written) on the host — the rootless daemon, `slirp4netns`, anything dev's user manager starts, and a `--network host` project container, which shares the host's network namespace. Those uids may open new host-local connections only to systemd-resolved's stub (`127.0.0.53`/`127.0.0.54`, port 53); every other host-local address, loopback included, is dropped. Accepted limits (tailscaled's LocalAPI relay, peers' LAN addresses): [Security](security.md) |
| `ufw`          | Adds one `ufw` rule so the devbox bridge reaches the gateway address ports publish on                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| `tmpfiles`     | Writes `/etc/tmpfiles.d/devbox-docker.conf` so `/run/devbox` exists before the daemon starts and on reboot                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| systemd unit   | Writes its own root-owned `/etc/systemd/user/docker.service` running `dockerd-rootless.sh --host unix:///run/devbox/docker.sock`, restarting the daemon when that file changes                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| Linger         | Runs `loginctl enable-linger dev`: gives the never-logged-in account a systemd user manager                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| `.env`         | Patches `DEVBOX_DATA_DIR=/home/dev`, `HOST_UID`/`HOST_GID=1001`, `DEVBOX_DOCKER_SOCKET_DIR=/run/devbox`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| Proof          | Outside `--check`: reads the daemon's version and security options as `dev` and runs `hello-world`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |

Finish with `./bin/devbox rebuild` as your own user.

## 💻 Laptop commands

Run these on the macOS laptop, from the repo checkout. `deploy` and every `sync` need `rsync` and `ssh` (`sync claude`
and `sync profile` also `jq`); a missing `rsync` fails up front with a `brew install rsync` remedy.
`deploy` needs **GNU** rsync, not macOS's `/usr/bin/rsync` — see [the FAQ](#rsync-is-not-gnu-rsync-on-deploy).

| Command                                 | What it does                                                                                                                       |
| --------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `deploy [HOST] [--start] [--force\|-f]` | Sync the runtime files of this repo to the workstation, optionally starting the container — see [`devbox deploy`](#devbox-deploy)  |
| `sync omp [HOST] [--allow-unguarded]`   | Apply the repo's OMP preset to this laptop and the devbox — see [`devbox sync omp`](#devbox-sync-omp)                              |
| `sync claude [HOST]`                    | Merge the repo's Claude Code preset into this laptop's and the devbox's settings — see [`devbox sync claude`](#devbox-sync-claude) |
| `sync identities [HOST]`                | Copy the laptop's identity registry into the devbox and apply it — see [`devbox sync identities`](#devbox-sync-identities)         |
| `sync profile [HOST]`                   | Render your profile into the agent context on this laptop and the devbox — see [`devbox sync profile`](#devbox-sync-profile)       |
| `agent install`                         | Install the agent git override on this laptop — see [`devbox agent install`](#devbox-agent-install)                                |

### `devbox deploy`

```
Usage: ./bin/devbox deploy [HOST] [--start] [--force|-f]

  HOST     Workstation SSH host (default: $DEVBOX_HOST, or DEVBOX_HOST in .push.env)

Options:
  --start  Run './bin/devbox start' on the workstation after syncing
  --force  Pass --force to that 'start': recreate even with live SSH sessions (needs --start)

Environment:
  DEVBOX_HOST         default SSH host; may also be set in .push.env beside this
                      repo (gitignored), since the alias is per-laptop
  DEVBOX_REMOTE_PATH  repo path on the workstation (default: ~/devbox)
```

No default host ships in the repo — the workstation's SSH alias is per-laptop, so it comes from an argument,
`$DEVBOX_HOST`, or `DEVBOX_HOST=<alias>` in `.push.env` beside the repo (gitignored), in that order; none of the three
set errors out naming all three ways to fix it.

Sync: only the runtime files travel — an allowlist, not the working tree: `bin/`, `container/`, `home/`, `Dockerfile`,
`docker-compose.yml` and `.env.example` (`.DS_Store` excluded inside them). It is `rsync -az --delete
--delete-excluded`, so anything else on the workstation — `docs/`, `.agents/`, `.claude/`, `.idea/`, `Makefile`,
prettier and editor configs, `README.md`, leftovers of earlier deploys — is removed, except the host's own state, which
is protected: `/.env`, `/data/`, `/docker-compose.override.yml` and `/.git/`. Uncommitted edits to the allowlisted paths
still ship, since it syncs the working tree of those paths. A new runtime path must be added to the `filters` array in
`cli/commands/deploy.sh`, or it never reaches the workstation.

`deploy` refuses to run unless the laptop's `rsync` is GNU rsync: macOS's `/usr/bin/rsync` is openrsync, which accepts
the protect rules and silently ignores them, so `--delete-excluded` would delete the workstation's `.env`, `data/` and
`.git`. `brew install rsync`, with Homebrew's `bin` ahead of `/usr/bin` on the `PATH`. It also checks for `rsync` on the
workstation first, printing the exact remedy if missing.

After the sync it runs `bin/devbox install` on the workstation, so `devbox` and its completion stay on its PATH; a
problem there is reported without failing the deploy. `--start` then runs the remote `start` over `ssh -t`, so a
recreate-with-sessions prompt reaches your terminal instead of failing the deploy; `--force` answers it up front, and is
rejected without `--start`.

```bash
echo 'DEVBOX_HOST=<workstation>' >.push.env   # once, so every bare ./bin/devbox deploy below resolves it
./bin/devbox deploy                            # sync only
./bin/devbox deploy --start                    # sync, then build and start
./bin/devbox deploy --start --force            # ... even if SSH sessions are connected
DEVBOX_REMOTE_PATH=~/devbox-test ./bin/devbox deploy <workstation>
```

### `devbox sync`

Every `sync` talks to the _container's_ sshd (`Host devbox`, port 2223), not the
workstation's, so the file lands inside bind-mounted `/home/dev`. None is part of a deploy: a redeploy updates the
workstation's checkout, never the live files in `/home/dev`. All resolve the host the same way: the `HOST` argument,
then `DEVBOX_SSH_HOST` from the environment or `.push.env` (the same gitignored file `deploy` reads), then `devbox`.
Before overwriting, each backs up the remote copy as `<file>.bak`, keeping one.

#### `devbox sync omp`

```
Usage: ./bin/devbox sync omp [HOST] [--allow-unguarded]

  HOST    devbox SSH host from ~/.ssh/config (default: $DEVBOX_SSH_HOST, then 'devbox')

Environment:
  DEVBOX_SSH_HOST   default SSH host; may also be set in .push.env
  OMP_CONFIG        source file (default: home/.omp/agent/config.yml in this checkout)
```

Applies the repo's OMP preset to both machines: first this laptop's `~/.omp/agent/config.yml` (created if absent, else
the replaced copy kept as `config.yml.bak` when it differed — OMP may have written a change there that never reached the
preset), then the devbox's, keeping one `config.yml.bak` there too. Only the preset travels, never the per-machine OMP
state (`agent.db`, `history.db`, sessions, memories, `models.yml`). Restart any running OMP session on either machine to
pick the new preset up.

> [!IMPORTANT]
> Refuses a preset without a top-level `bash:` block unless `--allow-unguarded`: the copy replaces each machine's whole
> `config.yml`, and with it the `bash.patterns` guardrail the installers seeded ([Toolchain](toolchain.md#-omp)). The flag is
> named for the guardrail rather than `--force` because `--force` elsewhere only ever means "past the live-session
> prompt".

#### `devbox sync claude`

```
Usage: ./bin/devbox sync claude [HOST]

  HOST    devbox SSH host from ~/.ssh/config (default: $DEVBOX_SSH_HOST, then 'devbox')

Environment:
  DEVBOX_SSH_HOST   default SSH host; may also be set in .push.env
  CLAUDE_SETTINGS   source file (default: home/.claude/settings.json in this checkout)
```

Applies the repo's Claude Code preset to both machines by _merging_ it, not copying it: `jq -s '.[0] * .[1]'` of the live
`~/.claude/settings.json` and the preset, so every key the preset does not set stays (the `hooks` `moshi-hook` and IDE
integrations write, `statusLine`), and the ones it sets (`model`, `permissions.deny`, `permissions.ask`) take its value,
the rule lists replaced whole. A top-level key removed from the preset entirely stays in the live files. This laptop's
file goes first (created if absent, else the previous copy kept as `settings.json.bak` when it changed); the devbox's is
then fetched over `ssh`, merged locally and copied back, keeping one `settings.json.bak` there too, and left untouched
when it already holds the preset. Needs `jq`, `rsync` and `ssh`. Restart any running Claude Code session on either
machine to pick the new preset up.

There is no `--allow-unguarded`: a merge cannot drop the live rules unless the preset sets an empty array. See
[Toolchain](toolchain.md#-claude-code) for the rules and [Security](security.md) for how they differ from OMP's.

There is no `sync codex`: Codex's guardrail is `~/.codex/rules/devbox.rules`, a file of its own that nobody else
writes, so nothing is merged or seeded. `bootstrap` (devbox) and [`agent install`](#devbox-agent-install) (laptop)
rewrite it on every run. To change it: edit `home/.codex/rules/devbox.rules`, `make lint`, run `devbox agent install`
on the laptop, then `deploy` and `bootstrap` for the devbox. See [Toolchain](toolchain.md#codex-guardrail).

#### `devbox sync identities`

```
Usage: ./bin/devbox sync identities [HOST]

  HOST    devbox SSH host from ~/.ssh/config (default: $DEVBOX_SSH_HOST, then 'devbox')

Environment:
  DEVBOX_SSH_HOST      default SSH host; may also be set in .push.env
  DEVBOX_IDENTITIES    source file (default: ~/.config/devbox/identities.conf)
```

Copies this laptop's identity registry into the devbox: validates it locally with `devbox-identities check` first (a
registry that does not validate must not be the one the devbox boots from), backs up the remote copy as
`identities.conf.bak`, `rsync`s the file over, then re-runs `container/bootstrap.sh` there over the same SSH connection
so `~/.ssh/config`, `~/.gitconfig`'s includes, `allowed_signers` and the agent gitconfigs catch up with whatever just
landed. If the copy lands but bootstrap fails, the error says so and points at `./bin/devbox bootstrap` on the
workstation.

#### `devbox sync profile`

```
Usage: ./bin/devbox sync profile [HOST]

  HOST    devbox SSH host from ~/.ssh/config (default: $DEVBOX_SSH_HOST, then 'devbox')

Environment:
  DEVBOX_SSH_HOST      default SSH host; may also be set in .push.env
```

Applies `~/.config/devbox/profile.json` (who you are and the tone agents take with you,
[Toolchain](toolchain.md#about-you-profilejson)) on both machines: validates it with `container/agent-context
validate-profile`, re-renders this laptop's `~/.config/devbox/agent-context.md` with it, backs up the remote copy as
`profile.json.bak`, `rsync`s the file over and re-runs `container/agent-context apply devbox` there — only the agent
context depends on the profile, so bootstrap does not run. The devbox renders with its own deployed `agent-context`, so
`deploy` first after changing it. New agent sessions on either machine pick the profile up.

```bash
./bin/devbox sync omp                    # home/.omp/agent/config.yml → laptop and devbox:~/.omp/agent/config.yml
./bin/devbox sync claude                 # home/.claude/settings.json merged into laptop and devbox:~/.claude/settings.json
./bin/devbox sync identities             # laptop → devbox:~/.config/devbox/identities.conf
./bin/devbox sync profile                # laptop → devbox:~/.config/devbox/profile.json, agent context re-rendered on both
./bin/devbox sync identities devbox-2    # a different ~/.ssh/config host
```

### `devbox agent install`

```
Usage: ./bin/devbox agent install
```

Idempotent: installs the same agent git override the devbox bootstraps. All of it is regenerated every run; nothing else
of yours is touched.

| Installed                                                                                                                                                                                                                                                                | Where                                                                                                                                                        |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `agent-launch` (the shared launcher body), `omp-launcher`, `claude-launcher`, `codex-launcher`, `claude-session-env` (the Claude desktop app's fence, below), `gh` shim, `fenced/git` shim, credential helper (`devbox-git-credential`), SSH fence (`devbox-git-no-ssh`) | `~/.local/libexec/devbox-agent`                                                                                                                              |

> `~/.config/devbox/identities.conf` is _not_ created for you — the example is a valid file, so seeding it would render
> agent gitconfigs authoring as `your-agent`; a missing registry fails the check and the run prints the `cp` command

`~/.config/devbox/secrets.env` and `~/.omp/agent/config.yml` (the OMP guardrail, [Toolchain](toolchain.md#-omp)) are
created from their templates if absent, then left alone — an existing OMP config without a `bash:` block becomes a
manual step. `~/.claude/settings.json` (the Claude Code guardrail, [Toolchain](toolchain.md#-claude-code)) is _merged_
with the preset when it is missing or holds no `permissions.deny` (needs `jq`; a changed existing file is kept as
`settings.json.bak`), left alone when it already has one, and an invalid JSON file becomes a manual step.

On every run it also appends a `SessionStart` hook running `claude-session-env` to `~/.claude/settings.json` when no
entry runs it yet, beside the herdr, `moshi-hook` and IDE ones: sessions the Claude desktop app starts, which no launcher
wraps, get the launcher's fence and `DEVBOX_ENV=laptop` through `CLAUDE_ENV_FILE` ([Git
Identities](git.md#claude-desktop-app)).

Codex gets no such hook (see the link for why): sessions the Codex desktop app starts are not fenced, only a `codex` started through its
launcher is ([Git Identities](git.md#codex-desktop-app)).

It also installs the agent context ([Toolchain](toolchain.md#-which-machine-the-agent-context)) through
`container/agent-context apply laptop`: `~/.config/devbox/agent-context.md` from the laptop template plus your
`~/.config/devbox/profile.json` when it exists, the `devbox-runtime` skill in `~/.agents/skills` with a
`~/.claude/skills` link, one `@~/.config/devbox/agent-context.md` line appended to `~/.claude/CLAUDE.md` if it is
missing, and a `~/.codex/AGENTS.md` link to the context when that file is absent, empty or a dangling link (Codex reads
that one file and expands no `@` imports). Nothing else in those files is touched. What it cannot fix in OMP's own
config (no `claude` in `enabledProviders`, a shadowing `~/.omp/agent/AGENTS.md`), in a `~/.codex/AGENTS.md` of your own
or a non-empty `~/.codex/AGENTS.override.md` (which shadows it), or an invalid profile becomes a manual step; a missing
profile only prints the optional `cp` command, since nothing seeds it either.

Reports whether `omp`, `claude` and `codex` resolve to their launchers — printing the `PATH` line for your shell rc as a
manual step until they do; an agent that is not installed is only noted, its launcher taking over once it is — plus the
remaining manual steps per registry identity: a read-only `GH_TOKEN_<SLUG>` line in
`secrets.env`, and its App's `{app-id,app.pem}` (mode 600) in its `app` directory — or, for an identity with no `app` set,
a GitHub App to create, since without one its agents can only read. See [Git Identities](git.md#-laptop-install).

## 🔗 `devbox install`

```
Usage: ./bin/devbox install
```

Makes `devbox` a command on this machine, the way `dot` is in the dotfiles: a symlink `~/.local/bin/devbox` onto this
checkout's `bin/devbox`, and the bash completion script at `~/.local/share/bash-completion/completions/devbox`
(`$XDG_DATA_HOME` respected), where bash-completion's lazy loader finds it on the first `<TAB>` after `devbox` — no rc
line, no startup cost. Idempotent: it touches only what differs, and refuses a `~/.local/bin/devbox` that is a real
file rather than replace someone else's command. A symlink onto another checkout is repointed at this one.

It finishes with the same checks `doctor` runs on both sides, exiting non-zero if one fails:

| Check           | Fix it reports                                                                                                                                                                              |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Symlink         | `bin/devbox install`                                                                                                                                                                        |
| Completion file | Missing, or not what this `bin/devbox` writes: `bin/devbox install`                                                                                                                         |
| PATH            | A fresh login shell (`$SHELL -lic`, clean environment) must resolve `devbox` to the symlink: the `PATH` line to add, or what shadows it                                                     |
| bash-completion | That shell must define bash-completion's lazy loader: `apt-get install bash-completion` (Ubuntu's default `~/.bashrc` loads it), or `brew install bash-completion@2` plus its `source` line |

The probe uses a fresh login shell because the calling one proves nothing: `devbox deploy` runs `install` over a
non-interactive `ssh`, which has neither `~/.local/bin` nor bash-completion. A login shell other than bash skips the
bash-completion check and prints the zsh line from [`devbox completions`](#-devbox-completions) instead.

`bin/devbox` finds its repo through the symlink (`readlink -f`, in macOS since 12.3), so every command behaves the same
whether you type `devbox` or `./bin/devbox`.

## 🩺 `devbox doctor`

```
Usage: ./bin/devbox doctor [host|laptop]
```

side this machine is — a Linux host runs the host checks, macOS the laptop checks — and refuses anywhere else (the
container has no docker and no keys). Naming a side the machine is not is refused like any other side-guarded command.

## 🧩 `devbox completions`

```
Usage: ./bin/devbox completions [bash|zsh]
```

Prints a completion script for bash (the default) or zsh. For bash, [`devbox install`](#-devbox-install) writes it
where bash-completion lazy-loads it, on both machines; zsh needs one line in `~/.zshrc`, after `compinit`:

```bash
source <(devbox completions zsh)
```

It completes commands, subcommands, flags, `doctor`'s side and the `[HOST]` of `deploy` and `sync`, the last from the
concrete `Host` aliases in `~/.ssh/config` and the files it `Include`s. The script registers for the name `devbox`,
which both shells also apply to a path ending in it — `./bin/devbox`, `bin/devbox` — and every `<TAB>` runs the script
exactly as typed, through its hidden `__complete` command, so it works wherever that path resolves. Workstation and
laptop commands are completed on both sides: the side guard applies when a command runs, not when it completes.
`./bin/devbox __complete sync omp ""` prints the raw candidates for debugging.

## 🪪 `devbox-identities`

```
Usage: devbox-identities list|dir-slugs|default|get|show|for|check|file|org-urls|alias-remotes|local-user-overrides|render ...
```

| Subcommand                      | What it does                                                                                                                     |
| ------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `list`                          | Slugs, in config order                                                                                                           |
| `dir-slugs`                     | Slugs claiming a tree, shortest dir first                                                                                        |
| `default`                       | The slug with no `dir` (the default identity)                                                                                    |
| `get <slug> <field>`            | One resolved field (see `identities.conf.example` for the list); `tag` is the ssh tag (empty when the plain key already matches) |
| `show <slug>`                   | Every resolved field for one identity                                                                                            |
| `for [directory]`               | The slug that owns a tree (default: `$PWD`)                                                                                      |
| `check`                         | Validate the registry; non-zero and a message per problem on error                                                               |
| `file`                          | Path to the registry in effect (`$DEVBOX_IDENTITIES_FILE`)                                                                       |
| `org-urls <slug>`               | `hasconfig:` URL patterns its `orgs` match                                                                                       |
| `alias-remotes`                 | Clones still on a `git@<slug>.<host>:` remote from the SSH-alias era                                                             |
| `local-user-overrides`          | Clones whose `.git/config` sets `user.name`/`user.email`, which outranks the agent author                                        |
| `render ssh-config`             | `~/.ssh/config`'s per-host and per-tag blocks                                                                                    |
| `render agent-gitconfig [slug]` | The root `agent.gitconfig`, or one identity's `[user]` block                                                                     |
| `render user-gitconfig <slug>`  | One identity's own gitconfig for its tree (`[user]` only)                                                                        |
| `render org-gitconfig <slug>`   | One identity's own gitconfig for its orgs (`[user]` + ssh tag)                                                                   |
| `render allowed-signers`        | `~/.ssh/allowed_signers`, one line per identity with a signing key                                                               |

Not part of `bin/devbox`: a separate, hand-written bash 3.2 script. Installed at `~/.local/libexec/devbox-identities` by
`container/bootstrap.sh` and `devbox agent install`; also sourceable as a library (`. devbox-identities`) by scripts
that need `di_slugs`, `di_default`, `di_get`, `di_for` or the renderers directly, which is how `bootstrap.sh`, `devbox
keys` and `devbox doctor laptop` read the registry. `DEVBOX_IDENTITIES_FILE` overrides the config path (used by `devbox
sync identities` to validate the laptop's copy before syncing it); `DEVBOX_IDENTITIES_TEMPLATE_DIR` points `render
agent-gitconfig` at `agent.gitconfig.tpl` when it isn't at the default `~/.config/devbox/git`.

```bash
devbox-identities list                    # one slug per line, e.g. personal, work
devbox-identities get work dir             # ~/projects/work
devbox-identities get work tag             # work, or empty if it shares the host's plain key
devbox-identities for ~/projects/work/app  # work (longest matching dir prefix wins)
devbox-identities check || echo 'fix identities.conf before bootstrapping'
```

## ✍️ Maintainer workflow

`bin/devbox` is **generated** — never hand-edit it. The source is `cli/`, built by bashly (settings in
`bashly-settings.yml` at the repo root).

### Edit the right files

| Path                  | Responsibility                                                                                                                                        |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `bashly-settings.yml` | bashly settings: source `cli/`, target `bin/`, strict mode, bash-version bouncer                                                                      |
| `cli/bashly.yml`      | Every command: group, help, filters (host/laptop), args, flags, env vars, dependencies                                                                |
| `cli/initialize.sh`   | Runs before any command: `REPO_ROOT`, `.env` paths, the laptop's install layout                                                                       |
| `cli/commands/`       | One body per command (`commands/sync/omp.sh`, `commands/docker/setup.sh`, ...)                                                                        |
| `cli/lib/`            | Shared functions: compose and the session guard, `.env` access, side detection, the doctors, docker setup steps, sync, logging, completion candidates |
| `bin/devbox`          | The generated script                                                                                                                                  |

### Regenerate and commit

To change a command, edit `cli/bashly.yml` (interface), `cli/commands/` (body) or `cli/lib/` (shared code), then run the
following from the repo root and **commit both** `cli/` and `bin/devbox`:

```bash
make build
```

- bashly formats the script with `shfmt -i 2` itself (`formatter` in `bashly-settings.yml`), so it matches every other
  shell file; `make check` fails when `bin/devbox` differs from a fresh build.
- The generated script is committed because the workstation has no Ruby; only a contributor who regenerates needs bashly
  (`brew install bashly` or `gem install bashly`).
- The side guard is a bashly `filters:` entry on each command (`filter_host` / `filter_laptop` in `cli/lib/machine.sh`),
  so a new command declares its side there.

## ❓ FAQ

### Why bashly instead of plain bash scripts?

One CLI replaced seven separate scripts that each reimplemented argument parsing, `--help` and the logging helpers;
bashly generates all of that from `cli/bashly.yml`, and the committed `bin/devbox` means neither machine needs Ruby or
bashly to run it. The cost is the regenerate step — see [Maintainer workflow](#-maintainer-workflow).

### `devbox` says it needs bash 4.2 on my Mac.

macOS ships bash 3.2 as `/bin/bash`. `brew install bash`, and make sure Homebrew's `bin` is on the `PATH` ahead of
`/bin` so `/usr/bin/env bash` finds it.

### Can I run `start`, `shell` and the other workstation commands from the laptop?

No — they drive the local Docker daemon and refuse to run off the host. Use `ssh <workstation> 'cd ~/devbox &&
./bin/devbox <cmd>'`, or `./bin/devbox deploy --start` for the common case.

### Is `--delete` dangerous?

Only the allowlisted paths (`bin/`, `container/`, `home/`, `Dockerfile`, `docker-compose.yml`, `.env.example`) are
synced, and `--delete-excluded` also removes everything else on the workstation's copy — `docs/`, `.agents/`, editor
configs, files left by older deploys. That is intentional: the remote is a runtime mirror, not a checkout. Host state is
protected and never touched: `.env`, `data/`, `docker-compose.override.yml` and `.git/`. Hand-added files in a synced
directory are removed too.

### `rsync is not GNU rsync` on `deploy`.

macOS's `/usr/bin/rsync` is openrsync. It accepts the protect rules `deploy` uses to keep the workstation's `.env`,
`data/` and `.git`, then ignores them, so `--delete-excluded` would wipe them — hence the refusal. `brew install rsync`
and put Homebrew's `bin` (`/opt/homebrew/bin`) ahead of `/usr/bin` on the `PATH`; `rsync --version` then reports `rsync
version 3.x`.

### Why is it `--allow-unguarded` on `sync omp` and not `--force`?

`--force` means exactly one thing across the CLI: go past the live-session prompt (`start`, `stop`, `rebuild`, `deploy
--start`). Skipping the OMP guardrail check is a different decision and gets its own name.

### Why does `sync claude` merge instead of copy like `sync omp`?

`~/.claude/settings.json` has other writers: `moshi-hook` and IDE integrations add `hooks` and `statusLine`, Claude
itself writes `model` (`/model`) and permission rules (`/permissions`). A copy would drop all of them, so the preset is
merged in (`jq -s '.[0] * .[1]'`): keys it does not set stay, keys it sets take its value, and the rule lists are
replaced whole, so a rule removed from the preset disappears too. Unlike that file, OMP's `config.yml` is not shared
with other writers, so `sync omp` copies it. A merge also cannot drop the live rules unless the preset itself sets an
empty array, so `sync claude` needs no `--allow-unguarded`. See [Toolchain](toolchain.md#-claude-code).

### `start` vs `rebuild` vs `update` — which do I need?

`start` after a compose, `.env`, `Dockerfile`, `container/` or `home/` change — rebuilds changed layers and recreates the
container. `rebuild` for a cache-free image, e.g. after bumping a pinned version. `update` neither: it upgrades OMP,
Claude Code, Codex and moshi-hook inside the running container, so no session is dropped and no repo change is applied.

### Does `bootstrap` overwrite my dotfiles?

Only the three generated ones — `~/.bashrc.d/devbox.sh`, `~/.bash_profile` and `~/.ssh/config` — rewritten from
templates every run, plus `~/.codex/rules/devbox.rules`, the Codex guardrail, a file of its own. `~/.gitconfig`,
`secrets.env`, `identities.conf` and the OMP config: created if absent, then left alone; the Claude Code settings are
merged with the preset only while they hold no `permissions.deny`; derived identity-registry values re-apply via
`git config --global` each run.

### `doctor` says `BIND_ADDR is X but Tailscale reports Y`.

The node's Tailscale address changed. `./bin/devbox env && ./bin/devbox start`.

### How do I tell whether the project Docker daemon is provisioned?

`sudo ./bin/devbox docker setup --check` reports every missing piece, changes nothing. `./bin/devbox doctor` also checks
the daemon is reachable and rootless from inside the container.
